### Часть 1. Архитектурная диаграмма
 
**Описание сервиса:**
 
Order Service управляет полным жизненным циклом ресторанного заказа: от создания и отправки на кухню до проведения оплаты и освобождения столика. Основные операции: создание заказа, проверка наличия блюд, резервация ингредиентов, формирование кухонного тикета, регистрация платежа. Основные сущности: `Order` (Заказ), `OrderItem` (Позиция заказа), `KitchenTicket` (Тикет кухни), `Payment` (Платёж).

### Часть 3. Domain Layer (Доменный слой)
 
**Доменные сущности**
 
**Entity 1: Order (Aggregate Root)**
 
```python
# domain/models/order.py
 
from domain.exceptions.domain_exception import DomainException
 
class Order:
    """
    Доменная модель: Заказ (Aggregate Root).
    Управляет жизненным циклом заказа в ресторане.
    Не зависит от фреймворков, БД и внешних сервисов.
    """
 
    ALLOWED_STATUSES = ["NEW", "IN_PROGRESS", "READY", "AWAITING_PAYMENT", "PAID", "CANCELLED"]
 
    def __init__(self, order_id: str, table_id: int, guests: int):
        self.id = order_id
        self.table_id = table_id
        self.guests = guests
        self.items = []         # List[OrderItem]
        self.status = "NEW"
        self.comment = None
        self.version = 1        # Для optimistic locking
 
    def add_item(self, item):
        """Добавить позицию в заказ"""
        if self.status != "NEW":
            raise DomainException(f"Нельзя изменить заказ в статусе {self.status}")
        self.items.append(item)
 
    def send_to_kitchen(self):
        """Отправить заказ на кухню"""
        if not self.items:
            raise DomainException("Нельзя отправить пустой заказ на кухню")
        if self.status != "NEW":
            raise DomainException(f"Заказ уже отправлен (статус: {self.status})")
        self.status = "IN_PROGRESS"
        self.version += 1
 
    def mark_ready(self):
        """Пометить заказ как выполненный кухней"""
        if self.status != "IN_PROGRESS":
            raise DomainException("Заказ ещё не готовится")
        self.status = "READY"
 
    def initiate_payment(self):
        """Инициировать оплату"""
        if self.status != "READY":
            raise DomainException("Заказ ещё не готов к оплате")
        self.status = "AWAITING_PAYMENT"
 
    def complete_payment(self):
        """Завершить оплату"""
        if self.status != "AWAITING_PAYMENT":
            raise DomainException("Оплата не была инициирована")
        self.status = "PAID"
 
    def calculate_total(self) -> float:
        """Вычислить итоговую сумму заказа"""
        return sum(item.price * item.quantity for item in self.items)
```

```python
class OrderItem:
    """
    Доменная модель: Позиция заказа.
    Представляет одно блюдо в составе заказа.
    """
 
    def __init__(self, dish_id: str, dish_name: str, quantity: int, price: float):

        self.dish_id = dish_id
        self.dish_name = dish_name
        self.quantity = quantity
        self.price = price
        self.comment = None
        self.station = None     # GRILL, PASTA, DESSERT, BAR — заполняется при отправке на кухню
```

**Value Object: OrderStatus**
 
```python
# domain/models/order_status.py
 
class OrderStatus:
    """
    Value Object: Статус заказа.
    Неизменяемый объект, описывающий состояние заказа.
    """
 
    NEW = "NEW"
    IN_PROGRESS = "IN_PROGRESS"
    READY = "READY"
    AWAITING_PAYMENT = "AWAITING_PAYMENT"
    PAID = "PAID"
    CANCELLED = "CANCELLED"
 
    TRANSITIONS = {
        NEW: [IN_PROGRESS, CANCELLED],
        IN_PROGRESS: [READY, CANCELLED],
        READY: [AWAITING_PAYMENT],
        AWAITING_PAYMENT: [PAID, READY],  # READY — при неудаче оплаты
        PAID: [],
        CANCELLED: [],
    }
 
    @staticmethod
    def can_transition(from_status: str, to_status: str) -> bool:
        return to_status in OrderStatus.TRANSITIONS.get(from_status, [])
```

**Бизнес-правила, реализованные в domain-слое:**
 
- Нельзя добавить позицию в заказ, если он уже отправлен на кухню (статус не `NEW`)
- Нельзя отправить пустой заказ на кухню
- Нельзя инициировать оплату, если заказ не в статусе `READY`
- Итоговая сумма заказа вычисляется как сумма `price * quantity` по всем позициям
- Версия заказа инкрементируется при каждом изменении статуса (optimistic locking)

```python
from abc import ABC, abstractmethod
from dataclasses import dataclass
from typing import List
 
@dataclass
class OrderItemCommand:
    """DTO: одна позиция в команде создания заказа"""

    quantity: int
    comment: str = None
 
@dataclass
class CreateOrderCommand:
    """DTO для команды создания заказа"""
    table_id: int
    guests: int
    items: List[OrderItemCommand]
    comment: str = None
    idempotency_key: str = None

    Вызывается REST-контроллером при POST /api/orders.

        """
        Создаёт заказ и возвращает его ID.
        :param command: Данные для создания заказа
        :return: ID созданного заказа (например, 'ORD-2024-0318')
        :raises DishUnavailableException: если блюдо в стоп-листе
        :raises TableOccupiedException: если столик уже занят

        pass
```

```python
class IOrderRepository(ABC):

    Исходящий порт: сохранение и загрузка заказов.
```

**Основная логика метода `create_order`:** получает команду от контроллера → проверяет идемпотентность и свободность столика → делегирует проверку ингредиентов в `IMenuInventoryPort` → создаёт `Order` aggregate с позициями в домене → резервирует ингредиенты → сохраняет через `IOrderRepository` → возвращает ID. Domain-логика (валидация статусов, расчёт суммы) живёт в `Order`, а не в сервисе.

```python
# infrastructure/adapter/out/in_memory_order_repository.py
from typing import Optional, Dict
 
class InMemoryOrderRepository(IOrderRepository):
    """
    Исходящий адаптер: хранение заказов в памяти.
    Реализует IOrderRepository для демонстрации без реальной БД.
    В Lab #5 будет заменён на PostgreSQLOrderRepository.
    """
 
    def __init__(self):
        self._orders: Dict[str, object] = {}       # order_id -> Order
        self._table_index: Dict[int, str] = {}     # table_id -> order_id
 
    def save(self, order) -> None:
        self._orders[order.id] = order
        if order.status in ("NEW", "IN_PROGRESS", "READY", "AWAITING_PAYMENT"):
            self._table_index[order.table_id] = order.id
        elif order.status == "PAID":
            self._table_index.pop(order.table_id, None)
 
    def find_by_id(self, order_id: str) -> Optional[object]:
        return self._orders.get(order_id)
 
    def find_by_table_id(self, table_id: int) -> Optional[object]:
        order_id = self._table_index.get(table_id)
        return self._orders.get(order_id) if order_id else None
```
 
**Принцип работы:** заказы хранятся в словаре `_orders` с ключом `order_id`. Дополнительный индекс `_table_index` позволяет быстро найти активный заказ по номеру столика. При переходе в статус `PAID` столик освобождается из индекса.

### Часть 6. Dependency Injection (Конфигурация зависимостей)
 
```python
# infrastructure/config/dependency_injection.py
 
from infrastructure.adapter.out.in_memory_order_repository import InMemoryOrderRepository
from infrastructure.adapter.out.stripe_payment_gateway import StripePaymentGateway
from infrastructure.adapter.out.console_notification_service import ConsoleNotificationService
from application.service.order_service import OrderService
 
class DependencyContainer:
    """
    DI-контейнер: связывает порты с адаптерами.
    Ключевой принцип: OrderService не создаёт зависимости сам —
    они передаются через конструктор (Dependency Inversion Principle).
    """
 
    def __init__(self):
        # 1. Создаём исходящие адаптеры (реализации портов)
        self.order_repository = InMemoryOrderRepository()
        self.payment_gateway = StripePaymentGateway()
        self.kitchen_notification = ConsoleNotificationService()
        self.menu_inventory = InMemoryMenuInventoryAdapter()
 
        # 2. Создаём application service с инжекцией зависимостей
        self.order_service = OrderService(
            order_repository=self.order_repository,
            menu_inventory_port=self.menu_inventory,
            payment_gateway=self.payment_gateway,
            kitchen_notification_port=self.kitchen_notification,
        )
 
    def get_order_service(self) -> OrderService:
        return self.order_service
 
# Точка входа
container = DependencyContainer()
```
 
**Как работает DI:** `DependencyContainer` создаёт конкретные реализации адаптеров (`InMemoryOrderRepository`, `StripePaymentGateway` и т.д.) и передаёт их в `OrderService` через конструктор. `OrderService` работает только с абстракциями (`IOrderRepository`, `IPaymentGateway`) — он не знает, что именно стоит за интерфейсом. Это позволяет в Lab #5 заменить `InMemoryOrderRepository` на `PostgreSQLOrderRepository` без изменения бизнес-логики.

## 6. Выводы
 
**Что получилось хорошо**
 
Удалось чётко отделить бизнес-логику (`Order`, `OrderItem`, `OrderStatus`) от инфраструктуры: domain-слой не содержит ни одного импорта из Flask, SQLAlchemy или Stripe. `OrderService` работает исключительно с абстракциями через порты, что делает его легко тестируемым с mock-объектами. Разделение на три независимые транзакции (создание заказа, отправка на кухню, оплата) хорошо ложится на три входящих порта — каждый use-case отвечает ровно за одну операцию.
 
**С какими трудностями столкнулись**
 
Было непросто определить, что именно относится к domain-слою, а что — к application. Например, логика распределения блюд по кухонным станциям (GRILL/PASTA/DESSERT) могла бы жить и в `Order`, и в `OrderService`. В итоге решено разместить её в `OrderService`, поскольку она оперирует понятием «станция», которое относится к инфраструктуре кухни, а не к самому заказу.
 
**Что узнали нового**
 
Изучил принцип Dependency Inversion на практике: `OrderService` принимает `IOrderRepository`, а не `InMemoryOrderRepository` — это значит, что в Lab #5 можно заменить хранилище на PostgreSQL без единого изменения в бизнес-логике. Понял, зачем нужны отдельные интерфейсы для каждого порта, даже если у них пока одна реализация: это граница для тестирования и точка расширения.
