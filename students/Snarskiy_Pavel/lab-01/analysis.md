# Анализ границ ответственности

**Система:** Ресторанная система «Прибыль на блюде» 🍽️  
**Сценарий:** Создание заказа и проведение оплаты

---

## 1. Транзакционные границы

### 1.1. Где начинается и заканчивается транзакция?

**Начало транзакции:** Официант нажимает кнопку "Создать заказ"

**Конец транзакции (успешный сценарий):**
- **Основная транзакция БД №1:** Заказ сохранён + Позиции созданы + Ингредиенты зарезервированы + Столик занят
- **Основная транзакция БД №2:** Тикет кухни сформирован + Блюда распределены по станциям + Статус заказа обновлён
- **Основная транзакция БД №3:** Платёж проведён + Заказ закрыт + Столик освобождён
- **Побочные эффекты (асинхронные):** Уведомления на кухонные дисплеи (KDS) отправлены

**Важно:** У нас три отдельные транзакции:
1. **Создание заказа + резервация ингредиентов + занятие столика** — атомарно
2. **Формирование тикета кухни + распределение по станциям** — атомарно (может откатиться независимо от п.1)
3. **Проведение оплаты + освобождение столика** — атомарно (может откатиться независимо от п.1 и п.2)

Если отправка на кухню не удалась, заказ остаётся в статусе `NEW`, и тикет можно создать позже.  
Если оплата не прошла, заказ остаётся в статусе `READY`, и оплату можно повторить.

### 1.2. Какие операции должны быть атомарными?

#### Транзакция №1: Создание заказа

**Атомарные операции (в одной БД-транзакции):**
1. Создание записи Order в таблице `orders`
2. Валидация позиций меню (наличие в меню, стоп-лист)
3. Вызов сервиса учёта ингредиентов для проверки и резервации остатков
4. Создание записей OrderItem в таблице `order_items`
5. Обновление статуса столика на `OCCUPIED` с привязкой к заказу
6. Создание связи Order ↔ Table

**Обоснование:** Заказ без зарезервированных ингредиентов может привести к ситуации, когда кухня не сможет приготовить блюдо. Столик должен занимать статус `OCCUPIED` атомарно с созданием заказа, чтобы исключить двойное бронирование.

**Пример сбоя:**
- Если заказ создан, но резервация ингредиентов не удалась → ROLLBACK всей транзакции
- Иначе получим «заказ-зомби» без зарезервированных продуктов

#### Транзакция №2: Отправка на кухню

**Атомарные операции (в одной БД-транзакции):**
1. Проверка текущего состояния заказа (версия, статус `NEW`)
2. Создание записи KitchenTicket в таблице `kitchen_tickets`
3. Создание записей TicketItem с распределением по станциям (GRILL, PASTA, DESSERT, BAR)
4. Обновление статуса заказа на `IN_PROGRESS`
5. Публикация события в transactional outbox

**Обоснование:** Если тикет создан, но статус заказа не обновился → кухня работает, а система считает заказ новым. Это приведёт к дублированию.

#### Транзакция №3: Проведение оплаты

**Атомарные операции (в одной БД-транзакции):**
1. Создание записи Payment в таблице `payments` со статусом `PENDING`
2. Обновление статуса заказа на `AWAITING_PAYMENT`
3. Публикация события `PaymentInitiated` в transactional outbox

После подтверждения от эквайринга (асинхронно):
1. Обновление статуса платежа на `COMPLETED`
2. Обновление статуса заказа на `PAID`
3. Освобождение столика (статус `FREE`, `active_order_id = NULL`)
4. Списание зарезервированных ингредиентов со склада

**Обоснование:** Регистрация платежа в БД должна предшествовать обращению к эквайрингу — это классический outbox pattern для финансовых операций. Столик освобождается только после подтверждения оплаты, чтобы избежать ситуации «ушёл не заплатив».

### 1.3. Какие операции могут быть асинхронными?

| Операция | Обоснование |
|----------|-------------|
| Отправка тикета на кухонные дисплеи (KDS) | Может быть отложена. Тикет уже создан в БД, KDS — это «best-effort» отображение |
| Списание ингредиентов со склада после оплаты | Eventual consistency допустима. Резервация уже есть, фактическое списание — расчётная операция |
| Запись событий в журнал событий (Events Log) | Eventual consistency допустима. События можно записать асинхронно через event sourcing |
| Обновление статистики выручки за смену | Можно пересчитать позже из журнала платежей |
| Синхронизация с системой лояльности (начисление баллов гостю) | Не влияет на текущий заказ |
| Отправка чека на email гостя | Приятный бонус, не критично для закрытия заказа |

**Принцип:** Если операция НЕ нарушает инварианты доменной модели при отказе — она может быть асинхронной.

| **Списание ингредиентов со склада после оплаты** | Асинхронная (через очередь) | Нет (резервация остаётся до успешного списания) | 3 попытки с задержкой 1s | Да |
| **Запись событий в журнал событий (Events Log)** | Асинхронная (event sourcing) | Нет (best-effort) | 3 попытки | Да (дедупликация по event_id) |
| **Обновление кэша выручки за смену (Redis)** | Асинхронная | Нет (eventual consistency) | 3 попытки с задержкой 1s | Да |

## 3. Обработка отказов внешних сервисов

### 3.1. Эквайринг-шлюз недоступен (Stripe)

**Проблема:** Платёжный шлюз не отвечает (таймаут, 503 Service Unavailable)

**Стратегия:**
1. **Таймаут:** 15 секунд на попытку списания
2. **Основная транзакция №3:** НЕ откатывается (платёж остаётся в БД со статусом `RETRY_PENDING`)
3. **Retry:**
   - Помещаем платёж в очередь `payment_retry_queue`
   - Фоновый worker повторяет попытку списания
   - Retry schedule: через 3 минуты, затем 9 минут, 27 минут
   - После 3 неудачных попыток → помечаем как `FAILED`, алертим менеджера
   - Предлагаем fallback: оплата наличными или другой картой
4. **Компенсация:** Столик остаётся `OCCUPIED` до успешной оплаты или ручного закрытия менеджером
5. **Уведомление пользователя:** "Оплата временно недоступна. Повторная попытка через 3 минуты. Можно предложить гостю оплату наличными."

**Обоснование:** Регистрация платежа в БД до обращения к эквайрингу (outbox pattern) гарантирует, что ни одна транзакция не потеряется. Столик нельзя освобождать до подтверждения оплаты.

### 3.2. База данных недоступна

**Проблема:** PostgreSQL не отвечает (connection refused, timeout)

**Стратегия:**
1. **Таймаут:** 5 секунд для connection, 30 секунд для query
2. **Основная транзакция:** ROLLBACK (заказ и тикет НЕ создаются)
3. **Retry:**
   - На уровне приложения: 3 попытки с экспоненциальной задержкой (1s, 2s, 4s)
   - Если все 3 попытки не удались → возвращаем 503 Service Unavailable
4. **Компенсация:** Нет (ничего не было создано)
5. **Offline-режим:**
   - Если официант работает с планшетом без соединения → сохраняем заказ локально (IndexedDB/SQLite)
   - При восстановлении связи → синхронизируем с сервером
6. **Уведомление пользователя:** "Не удалось создать заказ. Попробуй ещё раз или свяжись с менеджером."

**Обоснование:** БД — это критичный компонент. Без неё заказ не может существовать. Offline-режим важен для ситуаций с нестабильным Wi-Fi в зале.

### 3.3. Menu & Inventory Service недоступен

**Проблема:** Сервис проверки меню и остатков ингредиентов не работает

**Стратегия:**
1. **Таймаут:** 10 секунд
2. **Основная транзакция №1:** ROLLBACK (заказ НЕ создаётся без проверки ингредиентов)
3. **Retry:**
   - 3 попытки с задержкой 500ms
   - Если не удалось → возвращаем 500 Internal Server Error
4. **Компенсация:** Нет (заказ без проверки ингредиентов может привести к ситуации «блюда нет»)
5. **Fallback:**
   - Используем кэшированные данные о стоп-листе (TTL 5 минут из Redis)
   - Если кэш тоже недоступен → предлагаем официанту подтвердить наличие блюд вручную
6. **Уведомление пользователя:** "Не удалось проверить наличие блюд. Уточни у кухни и подтверди заказ вручную."

**Обоснование:** Проверка ингредиентов критична для качества обслуживания, но кэш позволяет деградировать gracefully при кратковременных сбоях.

### 3.4. Конкурентное изменение заказа перед отправкой на кухню

**Проблема:** Два сотрудника одновременно редактируют один и тот же заказ

**Стратегия:**
1. **Блокировка:** Используем optimistic locking через поле `version` в таблице `orders`:
   ```sql
   UPDATE orders
   SET status = 'IN_PROGRESS', version = version + 1
   WHERE id = 'ORD-2024-0318' AND version = 3;
   ```
   Если `affected_rows = 0` → кто-то уже изменил заказ → конфликт версий
2. **Основная транзакция №2:** ROLLBACK (тикет НЕ создаётся)
3. **Retry:** Показываем официанту актуальный состав заказа и просим повторно подтвердить отправку
4. **Компенсация:** Заказ остаётся в статусе `NEW` (откатывается только транзакция №2)
5. **Уведомление пользователя:** "Состав заказа был изменён. Проверь обновлённый заказ и подтверди отправку."

**Обоснование:** Optimistic locking предпочтительнее pessimistic в ресторанной системе, так как конфликты редки, а блокировка строк замедляла бы работу при высокой нагрузке в часы пик.

## 4. Идемпотентность

### 4.1. Проблема: Повторное нажатие кнопки "Создать заказ"

**Сценарий:** Официант дважды кликнул на кнопку из-за медленного Wi-Fi в зале

**Решение:**
1. **Frontend:** Блокировать кнопку после первого клика (disable button)
2. **Backend:** Проверять `idempotency_key` в запросе
   ```json
   {
     "table_id": 12,
     "items": [{"dish_id": "D-01", "qty": 1}],
     "idempotency_key": "waiter-42_table-12_2024-11-08_19-00-15"
   }
   ```
3. **Логика:**
   - При получении запроса проверяем таблицу `idempotent_requests`
   - Если `idempotency_key` уже есть → возвращаем кэшированный ответ (order_id)
   - Если нет → обрабатываем запрос и сохраняем в `idempotent_requests`
4. **TTL ключей:** 2 часа (в рамках одной рабочей смены)

**Пример таблицы:**
```sql
CREATE TABLE idempotent_requests (
  idempotency_key VARCHAR(128) PRIMARY KEY,
  endpoint        VARCHAR(255) NOT NULL,
  response_body   JSONB        NOT NULL,
  created_at      TIMESTAMP    DEFAULT NOW()
);

CREATE INDEX idx_idempotent_created ON idempotent_requests(created_at);
-- Очистка старых записей по cron (старше 2 часов)
```

### 4.2. Проблема: Дублирование тикетов на кухонный дисплей

**Сценарий:** KDS Worker получил событие дважды из-за retry в очереди

**Решение:**
1. В таблице `kds_notifications` добавляем уникальный ключ:
   ```sql
   CREATE UNIQUE INDEX idx_kds_dedup
   ON kds_notifications(ticket_id, station, notification_type);
   ```
2. При попытке добавить дубликат → игнорируем (ON CONFLICT DO NOTHING)
3. KDS также фильтрует дубликаты на уровне отображения по `ticket_id`

### 4.3. Проблема: Повторная попытка списания через эквайринг

**Сценарий:** Payment Worker повторно отправил запрос на списание, который уже был обработан

**Решение:**
1. При каждом обращении к Stripe передаём `idempotency_key` платежа:
   ```json
   {
     "amount": 522500,
     "currency": "rub",
     "source": "tok_xyz",
     "idempotency_key": "PAY-0318"
   }
   ```
2. Stripe гарантирует, что повторный запрос с тем же ключом не создаст двойного списания
3. На нашей стороне проверяем статус платежа перед каждой попыткой:
   ```sql
   SELECT * FROM payments
   WHERE id = 'PAY-0318' AND status NOT IN ('COMPLETED', 'FAILED');
   ```
4. Если платёж уже `COMPLETED` → пропускаем попытку, логируем предупреждение

### 4.4. Проблема: Повторное создание тикета для того же заказа

**Сценарий:** Официант дважды нажал "Отправить на кухню"

**Решение:**
1. Проверяем, есть ли уже активный тикет для этого заказа:
   ```sql
   SELECT * FROM kitchen_tickets
   WHERE order_id = 'ORD-2024-0318'
   AND status NOT IN ('COMPLETED', 'CANCELLED');
   ```
2. Если тикет уже существует → возвращаем его ID (не создаём новый)
3. Уведомление: "Заказ уже отправлен на кухню. Тикет: KT-318"

## 7. Выводы

### Ключевые решения:

1. ✅ **Три транзакции:** Создание заказа (Tx1), отправка на кухню (Tx2) и оплата (Tx3) — разделены для гибкости и независимого восстановления при сбоях
2. ✅ **Атомарность:** Заказ + резервация ингредиентов + занятие столика в одной транзакции; тикет кухни + распределение по станциям в другой; платёж + освобождение столика в третьей
3. ✅ **Асинхронность:** Отправка на KDS, списание ингредиентов и запись событий — через очередь
4. ✅ **Идемпотентность:** Используем `idempotency_key` для дедупликации заказов и idempotency key Stripe для дедупликации платежей
5. ✅ **Optimistic Locking:** `version` поле на заказе для защиты от конкурентного редактирования вместо pessimistic lock (низкая вероятность конфликта, высокая нагрузка в часы пик)
6. ✅ **Outbox Pattern:** Регистрация платежа в БД до обращения к эквайрингу — ни одна транзакция не потеряется
7. ✅ **Отказоустойчивость:** Не откатываем платёж при таймауте эквайринга; кэш стоп-листа для graceful degradation при недоступности Menu Service
8. ✅ **Retry:** Exponential backoff для эквайринга; линейный для KDS и ингредиентов
9. ✅ **Мониторинг:** Метрики для каждого критичного компонента + алерты
10. ✅ **Eventual Consistency:** События и статистика выручки записываются асинхронно через event sourcing

### Транзакционные инварианты:

- **Инвариант №1:** Заказ без зарезервированных ингредиентов недействителен → откатываем Tx1
- **Инвариант №2:** Столик не может быть занят двумя активными заказами → unique constraint на `tables.active_order_id`
- **Инвариант №3:** Тикет не может быть создан для заказа, который не в статусе `NEW` → проверка статуса + optimistic locking
- **Инвариант №4:** Столик освобождается только после подтверждения оплаты → обновление в рамках транзакции подтверждения

### Компромиссы:

- **Optimistic locking вместо pessimistic:** Ускоряет работу при высокой нагрузке в часы пик, но требует повторного подтверждения от официанта при конфликте версий
- **Кэширование стоп-листа (TTL 5 мин):** Позволяет работать при недоступности Menu Service, но с риском принять заказ на блюдо, только что добавленное в стоп-лист
- **Хранение idempotency keys 2 часа:** Занимает место в БД, но предотвращает дубликаты в рамках одной смены

### Риски:

⚠️ **Риск 1:** Очередь платежей может переполниться при массовом сбое эквайринга в часы пик
- **Митигация:** Лимит очереди + алерт при превышении 1000 сообщений + автоматический switch на резервный эквайринг

⚠️ **Риск 2:** Устаревший кэш стоп-листа может привести к принятию заказа на отсутствующее блюдо
- **Митигация:** TTL кэша 5 минут + инвалидация кэша при обновлении стоп-листа через событие `DishAddedToStopList`
